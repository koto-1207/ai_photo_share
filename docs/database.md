# データベース設計

- DB: SQLite（PeeWeeで操作する）
- 前提: [requirements.md](requirements.md) / [routes.md](routes.md) / [screens.md](screens.md)

## 1. テーブル一覧

| テーブル | 役割 | 実装する時期 |
|---|---|---|
| User | アプリを使う人の情報を保存する | 必須 |
| Post | 投稿（写真とキャプション）を保存する | 必須 |
| Like | 「誰が」「どの投稿に」いいねしたかを保存する | 余裕があれば |
| Comment | 投稿へのコメントを保存する | 参考（今回は作らない） |

## 2. 関係（ER図）

```
User 1 ──── * Post        1人のユーザーは、複数の投稿を持てる
User 1 ──── * Like        1人のユーザーは、複数のいいねをできる
Post 1 ──── * Like        1つの投稿は、複数のいいねをもらえる
```

`1 ── *` は「1対多」の関係を表す。「多」の側のテーブルが、外部キーで「1」の側を指す。

## 3. 各テーブルの設計

### 3-1. User（ユーザー）

**なぜ必要か**: ログインするには、ユーザー名とパスワードをどこかに保存しておく必要がある。また、投稿に「誰が投稿したか」を記録するときに、このテーブルを参照する。

| カラム | データ型 | 主キー | 外部キー | ユニーク | 必須 | 説明 |
|---|---|---|---|---|---|---|
| id | 整数（AutoField） | ○ | | ○ | ○ | 自動で採番される番号 |
| username | 文字列（CharField, 30文字） | | | ○ | ○ | ログインと画面表示に使う名前 |
| email | 文字列（CharField, 255文字） | | | ○ | ○ | 保存と重複チェックだけに使う（ログインには使わない） |
| password_hash | 文字列（CharField, 255文字） | | | | ○ | ハッシュ化したパスワード。元のパスワードは保存しない |
| created_at | 日時（DateTimeField） | | | | ○ | 登録した日時 |

- **ユニーク制約**: `username`、`email`（同じ名前やメールアドレスで2回登録できないようにする）
- **インデックス候補**: `username`（ログインのたびに検索するため。ユニーク制約を付けると自動でインデックスが作られる）

### 3-2. Post（投稿）

**なぜ必要か**: アプリの中心となるデータ。写真そのものはフォルダに保存し、このテーブルには「どのファイルか」「誰が」「いつ」「どんなキャプションで」投稿したかを保存する。

| カラム | データ型 | 主キー | 外部キー | ユニーク | 必須 | 説明 |
|---|---|---|---|---|---|---|
| id | 整数（AutoField） | ○ | | ○ | ○ | `/posts/<post_id>` のURLで使う |
| user | 整数（ForeignKeyField） | | User.id | | ○ | 投稿者 |
| image_filename | 文字列（CharField, 255文字） | | | ○ | ○ | サーバーで作り直したファイル名（UUID）。例: `3f2a9c....jpg` |
| caption | 文字列（CharField, 200文字） | | | | | キャプション。空でもよい |
| created_at | 日時（DateTimeField） | | | | ○ | 投稿日時 |

- **外部キー**: `user` → `User.id`（投稿とユーザーをつなぐ）
- **ユニーク制約**: `image_filename`（1つの画像ファイルを2つの投稿で使わないようにする）
- **インデックス候補**: `created_at`（一覧を新しい順に並べるため）、`user`（外部キーにはPeeWeeが自動でインデックスを作る）

**画像のファイル名だけを保存する理由**: 画像の中身をDBに入れるとDBが重くなる。また、`uploads/xxx.jpg` のようにパスごと保存すると、フォルダの場所を変えたときにデータを全部直す必要がある。ファイル名だけなら、フォルダの場所は設定で変えられる。

### 3-3. Like（いいね）※ 余裕があれば実装する

**なぜ必要か**: いいねは「誰が」「どの投稿に」という2つの情報の組み合わせ。Post に「いいね数」のカラムを置くだけでは、誰がいいねしたか分からず、取り消しや二重いいねの防止ができない。そこで、1件のいいねを1行として記録する専用のテーブルを作る。いいね数は、この行を数えれば分かる。

| カラム | データ型 | 主キー | 外部キー | ユニーク | 必須 | 説明 |
|---|---|---|---|---|---|---|
| id | 整数（AutoField） | ○ | | ○ | ○ | 自動で採番される番号 |
| user | 整数（ForeignKeyField） | | User.id | | ○ | いいねした人 |
| post | 整数（ForeignKeyField） | | Post.id | | ○ | いいねされた投稿 |
| created_at | 日時（DateTimeField） | | | | ○ | いいねした日時 |

- **外部キー**: `user` → `User.id`、`post` → `Post.id`。投稿を削除したら、その投稿のいいねも自動で削除する（CASCADE）
- **ユニーク制約**: `(user, post)` の組み合わせ（複合ユニーク）。1人が同じ投稿に2回いいねできないようにする
- **インデックス候補**: `(user, post)`（ユニーク制約で自動で作られる）、`post`（投稿ごとのいいね数を数えるため）

### 3-4. Comment（参考・今回は作らない）

**なぜ必要か**: 1つの投稿に、複数の人がコメントを書ける。Like と同じく「誰が」「どの投稿に」に加えて、本文を保存する。

| カラム | データ型 | 外部キー | 説明 |
|---|---|---|---|
| id | 整数（AutoField） | | 主キー |
| user | 整数（ForeignKeyField） | User.id | コメントした人 |
| post | 整数（ForeignKeyField） | Post.id（CASCADE） | コメントされた投稿 |
| body | 文字列（TextField） | | コメント本文 |
| created_at | 日時（DateTimeField） | | コメントした日時 |

### 3-5. 余裕があれば追加する機能で必要になるカラム（参考）

| 機能 | 追加するカラム | 説明 |
|---|---|---|
| 画像の縮小・サムネイル | Post.thumb_filename（CharField, 255文字） | 縮小した画像のファイル名 |
| アイコン画像 | User.icon_filename（CharField, 255文字、空でもよい） | アイコン画像のファイル名。未設定なら空 |

## 4. PeeWeeで実装する場合の注意点

1. **主キーは書かなくてよい**: `id` カラムは、PeeWeeが自動で作る（AutoField）。
2. **日時の初期値は関数を渡す**: `default=datetime.now` と書く。`datetime.now()` と括弧を付けると、アプリを起動した時刻で固定されてしまう。
3. **外部キーには `backref` を付ける**: Post の `user` に `backref="posts"` を付けると、`user.posts` でそのユーザーの投稿をまとめて取れる。
4. **SQLiteでCASCADEを効かせる**: SQLiteは、初期設定では外部キーの制約が無効になっている。DBに接続するときに `pragmas={"foreign_keys": 1}` を指定する。
5. **複合ユニークは `Meta` に書く**: Like の `(user, post)` は、`class Meta` の `indexes` に `((("user", "post"), True),)` のように指定する。`True` がユニークを表す。
6. **インデックスは `index=True` で付ける**: Post の `created_at` のように、1つのカラムに付けるときに使う。`unique=True` を付けたカラムには、インデックスが自動で作られる。
7. **一覧はJOINで取得する**: 投稿者名を表示するために投稿ごとにUserを取りに行くと、クエリの回数が投稿の数だけ増える（N+1問題）。`Post.select(Post, User).join(User)` のようにまとめて取得する。
8. **重複エラーに備える**: ユーザー名やメールアドレスが重複すると `IntegrityError` が発生する。登録処理では、事前に存在をチェックするか、このエラーを捕まえてメッセージを表示する。
9. **テーブルは少しずつ作る**: 最初は `create_tables([User, Post])` だけにして、いいねを実装するときに Like を追加する。`create_tables` は、すでにあるテーブルを作り直さない（`safe=True` が初期値）。
10. **カラムを後から変えるとき**: `create_tables` では、既存のテーブルにカラムを追加できない。開発中はDBファイルを削除して作り直すのが簡単（データは消える）。
11. **DBファイルはGitに入れない**: `app.db` などのDBファイルは `.gitignore` に追加する。
